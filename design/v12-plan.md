## 〇、给执行者的说明

### 开工前

1. 读 `AGENTS.md`、`README.md`、`design/v11-playtest.md`、`design/review-v11.md` 和这份方案。
2. **一次只做一个版本。** 版本内按工作项顺序做，每项一个或几个提交，每个提交的测试都要是绿的。
3. **方案没写到、又必须定的地方，先选最小的做法。** 在本版试玩记录的「已知限制」里写一句。不要自己扩出新系统。
4. **第十节「需要拍板」里的事，不要自己替用户决定。** 对应的工作项按推荐的默认做法实现，并留开关。

### 不能破坏的约定

这些是现有架构的底线，每个工作项都要守住。

- **只有一个规则入口。** 玩家操作、网页、CLI、自动玩家都走 `engine.execute(state, name, args)`。新命令写成 `engine.py` 里的函数，加进 `COMMANDS`。参数要有类型注解（`str`、`int`、`list`），`execute` 靠它校验。
- **命令先检查后修改。** 所有 `check()` 都放在第一处修改状态之前。`execute` 在副本上执行，抛错就丢弃副本。但自动推进（W2）会在 `advance` 里直接调用命令函数，没有副本保护，所以先检查后修改是硬要求。
- **快照只读。** `view.snapshot` 和它调用的一切（`assist.*`、`rating.view`、`chapters.view` 和新增的 `guide.*`），都不能改状态，也不能产生新的随机结果。需要试算时，用 `assist._try` 在副本上跑。
- **随机都用带键的 `model.rand(s, *keys)`。** 同一组键永远得到同一个结果，不要用全局随机。新的随机点要起新的、能说明来源的键，比如 `rand(s, "incident", p["id"], key, attempt)`。
- **新事件要登记两处。** 加进 `events.TEMPLATES`，同时加进 `design/api/state-v2.schema.json` 的事件枚举。快照新增顶层字段也要写进 schema，然后运行 `uv run python scripts/generate-api-types.py` 重新生成 `web/api-types.d.ts`。
- **自动玩家只能读公开信息。** `bot.py`、`scripts/playtest-*.py` 不能读候选的 `truth`。分析脚本可以读真值算结果，但要在脚本开头写明「这是分析，不是玩家策略」。
- **界面只发命令，不算规则。** 门槛、价格、机会这类数字都在服务端算好，放进快照。`panels.js`、`ui.js`、`app.js` 只负责显示和发送命令。
- **页面不加外部资源。** 不加远端脚本、字体、图片。安全策略只允许同源脚本和 `data:` 图片。新的 JS 文件要加进 `server.py` 的白名单，还要在 `scene/index.html` 里引用。
- **保护玩家存档。** 开发和测试用独立端口（8921–8959）和 `.artifacts/` 下的独立存档，不碰 `saves/`。存档格式一变，`VERSION` 就要加一，并且新版能读旧档、绝不改写旧档（见 W0）。

### W0 存档 v10、存档文件规则、编年史、游玩记录

**为什么：** v0.12 要存新字段。v0.11 线上的存档规则（v8 原档加 `-v11.json`）也要推广成通用的。任期回顾（W19）需要从现在起就攒下完整的大事记。平衡需要真人数据。

**存档格式。** 改 `model.py`：

```python
VERSION = 10
READABLE = (8, 9, 10)
# 哪个格式由哪一版游戏写；v8 是原文件（无后缀）
SUFFIX = {8: "", 9: "-v11", 10: "-v12"}
```

- `loads()` 先记下原版本，再循环调用迁移，直到 `version == VERSION`，最后写 `s["migrated_from"] = 原版本`。

**找存档、写存档。** 在 `model.py` 新增：

```python
    """返回 (从哪里读, 往哪里写)。

    base = 去掉 path 文件名里已知后缀（-v11、-v12）后的路径。
```

### W1 引导跟着章节走，「下一件事」带出成长动作

**为什么：** 只点推荐的新手玩到第 12 年，团队还是开局两个人。第 2 章「一位伙伴晋升精英」的条件早就满足了，但左上角一直写「按 1× 让时间走起来」。晋阶、扩建、邀请伙伴、个人课题都藏在别的标签页里。

**玩家看到什么。**

- **左上角引导条。** 顺序是：待决定 → 现金警告 → 可恢复的暂缓项目 → **成长建议** → 「▶ 开始」。成长建议是一个按钮，点了直接执行。例如：
  - 「**晋阶陈一鸣** · 第 2 章需要一位精英 · ¥90 万」；
  - 「**邀请米可** · 临床有人了，等效性不用再外包 · ¥70 万」；
  - 「**仿制药都做过了** · 改良药还差：制剂能力 50（苏小禾 44）」。
- **研发面板。** 在「进行中」下面加一栏「接下来可以做」，最多三条，内容和引导条同源。
- **时间暂停。** 时间在走时，第一次出现某个成长机会（某人可晋阶、买得起下一档场地、新伙伴可邀请、个人课题解锁、改良药或创新药解锁），时钟会停一次。同时弹提示：「可以晋阶了：陈一鸣」。同一个机会只停一次。

**规则与快照。** 新文件 `career/guide.py`，全部只读：

```python
def suggestions(s, limit=3) -> list[dict]:
    """按优先级给出最多 limit 条成长建议。每条：
    {key, kind, title, text, chapter: bool, command, args, ok, error, tab, route}
    kind ∈ promote / upgrade / equipment / hire / collaborate / personal / mentor / project / services
    命令类建议都先用 assist._try 在副本上试一次；ok=False 的只在 chapter=True 时保留，并显示 error。
    最多试 4 次，控制快照耗时。"""


def moments(s) -> list[tuple[str, dict]]:
    """当前成立的「第一次」成长时刻，返回 (key, 事件数据)。key 的格式：
    promote:<hero>:<下一阶>   upgrade:<下一档>   hire:<角色>（只算 tier ≥ 2 和李天天）
    personal:<hero>   route:improved   route:innovative"""
```

**优先级。** 前面的先占位：

1. **当前章节的推进手段（`chapter=True`）。** 给 `chapters.CHAPTERS` 每章加 `levers: callable(s) -> list[dict]`：
   - **第 1 章：** 不给，靠决定卡。
   - **第 2 章：**
     - 有人可晋阶 → `promote`，挑费用最低的人；
     - 少于两款药 → `project`；
     - 星级「搬进联合研发所」：`available_cash ≥ 成本 + 300` 时给 `upgrade`；
     - 星级「完成一次带教」：有可行的导师和学生组合时给 `mentor`。
   - **第 3 章：**
     - 创新药可开始 → `project`（`route=innovative`）；
     - 不能开始 → 给出差的第一项条件，以及能补上它的动作（晋阶、升级设备、扩建）。
   - **第 4 章：**
     - 缺「专业研究院」→ `upgrade`；
     - 缺「一位生物或药化大师」→ `promote`；
     - 条件都满足但没有在研的难治项目 → `project`（`route=innovative`）。
   - **第 5 章：**
     - 列出四道关里还缺的人；
     - 能邀请的给 `hire` 或 `collaborate`；
     - 已在职的列出名字，不用动作。
2. **任何可晋阶的伙伴：** `promote`。
3. **研究台空、有人空闲：** `project`。`route` 按「仿制 → 改良 → 创新」选第一条有可开始项目的路线。都没有时，`ok=False`，`text` 写出差的条件。
4. **个人课题可开始：** `personal`。点了打开人物卡，因为要选搭档。
5. **可邀请的新伙伴：** `hire`。只给能负担的人，专业空缺的优先。
6. **有空闲伙伴、服务有推荐人选：** `services`。

**引擎。**

- **`engine.advance`：** 每周末尾（`retirements` 之后、`rating.finish_term` 之前）调用 `guide.moments(s)`。对 `tips_seen` 里没有的 key，追加进去，并发事件 `growth_ready`，数据为 `{key, kind, title, text}`。
- **`engine.next_event`：** 循环里只要本周出现 `growth_ready` 事件就停，写法和 `batches` 的判断一样。

### W10 主动技能（每人一个，带冷却）

**为什么：** 有了主动技能，两个能力相同的人也能玩出不一样的打法。卡在决定上时，玩家多了一个「找谁帮忙」的选择。

**规则。**

- **新文件 `career/skills.py`。** 技能数据写在 `data/abilities.json`，每人加 `active` 字段：

```json
"active": {"name": "放大一次", "text": "...", "kind": "improve", "params": {"stat": "quality", "amount": 4},
           "scope": "project", "when": "preclinical", "cost": 40, "cooldown": 96}
```

- **原语：** `kind` 只能是下面 9 种之一。每种原语在 `skills.py` 里实现一次，并且都要先检查后修改。

| kind | 作用 | 限制 |
|---|---|---|
| `shorten` | 进行中的阶段剩余周数减 `weeks`（最少剩 1 周），剩余费用不变（`cost_per_week` 按新周数重算） | 项目在 running 且这个人在团队里 |
| `reveal` | 立刻对一项指标做一次观测，等于免费的专项复核，噪声为 `sigma`。用 `science.observe`，标签 `skill-<hero>-<n>` | 项目在 ready |
| `improve` | 当前候选的一项指标真值和估计同时 + `amount`，没有代价 | 临床前（index < 2），每个项目每个技能一次 |
| `candidate` | 选候选时多生成一个候选：`generate_candidates` 拆出一个 `make_candidate(s, p, i, label, offsets)`，用新下标 | 项目在 selecting |
| `limit` | 下一阶段（或当前 ready 的阶段）某项门槛 + `delta`（负数是降低）：写进 `p["adjust_next"]`，`run_phase` 时合并进 `p["adjust"][key]` | 项目在 ready 或 result |
| `rescue` | 失败不超过 8 周、且每项差距 ≤ 6（显示为 60）的临床阶段，改为可补正：`status = "problem"`、`ended = None`，保留 `credited` | 每个项目一次，和奥马尔觉醒共用 `reanalyzed` 标记 |
| `xp` | 一位同专业、阶位更低的伙伴立刻获得 `amount` 经验 | 有这样的人 |
| `product` | 一款在售产品的峰值 × `factor`（每个产品一次），或毛利 + `margin` | 有在售产品 |
| `service` | 这个人正在做的技术服务立刻完成并回款 | 她在做服务 |

- **解锁条件：** 见习角色晋升精英（rank ≥ 2）后解锁；精英以上的角色加入时就有。
- **冷却：** 默认 96 周，传奇 144 周。记在 `h["skill_ready"]`，值为可再用的周数，迁移时补 0。
- **新命令：** `use_skill(character: str, project: str = "", product: str = "")`。

**21 个技能见附录 C。** 数值要先用模拟校准，看主动技能对证据型玩家的评级中位数影响，目标是 +3 到 +6 分。超过就降数值。

**界面。**

- **人物卡：** 专长一节下面加「主动 · 放大一次」：说明、冷却状态，以及「使用」按钮。需要选项目或产品时弹一个小选择框，只列符合条件的项目。
- **决定卡：** 列出现在能用、对这个项目有效的技能，作为次按钮：「可用专长：林巧·放大一次 · ¥40 万」。这是主动技能最重要的入口。快照 `project.skills` 由 `skills.usable(s, p)` 给出，只读。
- **场景：** 用技能时发 `talent_triggered`，沿用 W9 的飘字。

**自动玩家。** 证据型玩家加最简单的用法：「决定卡上有可用技能、且能直接提高本阶段机会时就用」。新手不用。

**测试：`tests/test_active_skills.py`。** 每种原语一个测试，加上冷却、解锁条件、重放一致、快照只读。

### W12 失败事件卡

**为什么：** 现在的失败只是一个没过线的数字，失败也该有故事可讲。

**规则。**

- **新文件 `data/incidents.json`。** 按「阶段组 × 失败指标」给 2–3 个原因，见附录 D。阶段组：
  - `build`：处方、质量、改良设计、优化；
  - `be`；
  - `clinical`：I、II、III、桥接、确认；
  - `review`。
- **每个原因有：**
  - `title`：一句话；
  - `text`：两句话；
  - `expert`：哪个专业的人最懂；
  - `talent`：哪位角色的专长对口，可以为空。
- **生成：** 在 `engine.finish_phase` 失败分支里，用 `rand(s, "incident", p["id"], key, p["repairs"])` 从对应失败指标的原因里选一个，写 `p["incident"] = {key, title, text, options}`。
- **选项**由 `incident_options(s, p)` 按公开状态算出，每项映射到已有命令或带修正的新命令：
  - 「按原方案补正」：现在的 `rework`。
  - 「请{专业}的{人名}来看」：有对口专业、能力 ≥ 60、空闲的伙伴时出现。新命令 `rework_expert(project, hero)`，6 周、¥130 万，补正幅度从 +6 提到 +9。
  - 「让{角色}试试」：对口专长的角色在职且空闲时出现，补正幅度 +12。
  - 「换候选」：index < 2 时出现，就是现在的 `switch_candidate`。
  - 「止损」：失败地图记一笔。司马衡在职时文案写「司马衡会记住这次」。
  - 临床阶段失败、无法补正时：只有「止损」，以及奥马尔的主动技能 `rescue`（W10），如果可用。
- **自动推进的仿制药**遇到失败卡，就停下来交给玩家（替换 W2 里的临时做法）。

**界面。** 决定卡在「差一点」的位置，换成事件卡：标题、两句说明、选项按钮。每个按钮写周数、费用和相关的人。

**测试。**

- 同一个失败每次抽到同一个原因。
- 选项按在职情况出现。
- `rework_expert` 和带专长的补正幅度正确。
- 选「止损」后的状态和现在的 `terminate` 一致。

### W13 花钱的出口

**为什么：** 证据型玩家 20 年末现金中位数 4–5 亿，后期每周净赚 100 多万，却没有花钱的地方。下面四个出口，都是把钱换成评级上的某一项。

| 出口 | 命令 | 费用 | 效果 | 换成什么 |
|---|---|---|---|---|
| 自有产线 | `build_line(product)` | 仿制 500、改良 800、创新 1,500 万；运营每周 1 万 | 这款产品改为自产（`production = "self"`）：毛利 仿制 +0.10、其他 +0.06；不受供货折减影响 | 经营稳健 |
| 患者援助计划 | `access_program(product, on: int)` | 每周花掉这款产品销售额的 12% | 这款产品的患者人次 ×1.6（只影响评级的惠及患者，不影响收入）；每满一年声誉 +1 | 惠及患者、行业声誉 |
| 青年学者计划 | `fund_fellowship()` | 每期 600 万，最多 5 期，要求联合研发所及以上 | 每期团队传承 +8 点；第 3 期起，每期让一位见习伙伴立刻获得 10 经验 | 团队传承 |
| 临床病房 | `build_ward()` | 1,200 万，最多 2 个，运营每周 2 万 | 自营临床席位 +1 | 更多创新药并行 |

- **产线数量**受 `FACILITIES[facility]["lines"]` 限制，这个字段已经有了（0、2、5、9），`economy.production_lines` 也已经有了。新命令要检查 `production_lines(s) + 1 ≤ lines`。
- **改高铁峰的专长**（要用户确认，见第十节）：「自建产线：建线费用 −30%，自有产线毛利再 +6%」。现在的「在职时自主产品毛利 +6%」不再作用于委托生产的产品。
- **界面：**
  - 产品卡加「建自有产线」和「患者援助」开关；
  - 研究所面板加「青年学者计划」和「临床病房」；
  - 引导（W1）在现金超过 1 亿、且有对应条件时，给出其中一项建议。

**自动玩家。** 证据型玩家：现金超过 8,000 万时，按「产线 → 病房 → 学者计划 → 患者援助」的顺序用掉多余的现金，并保留 3,000 万。

**验收。** 证据型玩家 48 局：

- 20 年末现金中位数 ≤ 2.5 亿；
- 评级中位数不低于 v0.12；
- 停业不增加。

## 九、附录 D · 失败原因（W12）

**处方、质量、改良设计、优化 · 工艺稳定**

- 放大后晶型转变（专业 proc，专长 crystal）
- 批间含量波动（专业 proc，专长 pill）
- 辅料换了批次（专业 proc）

**处方、质量 · 安全窗口（仿制药是杂质）**

- 基因毒杂质超限（专业 tox，专长 bubble）
- 储存中降解产物增加（专业 tox）
- 残留溶剂偏高（专业 chem）

**生物等效性 · 暴露与等效**

- 高脂餐后吸收偏低（专业 clinical，专长 ruler）
- 溶出曲线在 pH 6.8 掉队（专业 proc，专长 crystal）
- 参比制剂批次差异（专业 clinical）

**临床 · 获益潜力**

- 安慰剂组反应偏高（专业 clinical，专长 curve）
- 入组人群太宽（专业 bio，专长 bridge）
- 剂量选低了（专业 clinical）

**临床 · 安全窗口**

- 肝酶升高（专业 tox，专长 judge）
- QT 间期延长信号（专业 tox，专长 guardian）
- 输注反应（专业 clinical）

**临床 · 暴露与等效**

- 个体差异太大（专业 clinical）
- 半衰期比预期短（专业 chem，专长 forge）
- 食物影响明显（专业 clinical）

**审评 · 工艺稳定**

- 现场核查发现记录缺口（专业 proc，专长 judge）
- 稳定性数据不够长（专业 proc）

每个原因再写一段两句话的 `text`，执行时补写。语气参考 `chapters.STORIES`：平实、具体，不夸张。

## 十一、风险

- **W2 的自动推进最容易出错。** 引擎第一次在 `advance` 里替玩家执行命令。先写好「先检查后修改」的测试再动手。
- **W3、W4 改动的是玩家最常看的界面。** 每一步都要截图对比。不要一次改完再看。
- **W11 和 W13 会改动平衡。** 一次只改一项，每改一项跑一次模拟。阿尔茨海默的边界结果是回归基线，不能变。
- **快照耗时。** W1 的建议、W2 的估算、W10 的可用技能，都会在快照里试执行命令。每个工作项做完都要量一次，超过 25 毫秒就加缓存（按 `revision`），或者减少试算次数。
- **自动胜率不是人类胜率。** 每份试玩记录都要写明，并且尽量附上游玩记录（W0）的真人数据。
